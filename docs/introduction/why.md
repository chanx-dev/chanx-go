# Why chanx-go?

Go has excellent WebSocket libraries, gorilla/websocket and coder/websocket, but they
stop at the socket. Everything after the upgrade is left to you, and every team writes
the same code: a read loop, a `switch` on a type field, hand-rolled validation, a hub
for rooms, Redis pub/sub for more than one process, and docs that drift from the code.

chanx-go is that code, written once and tested.

## What you get

| You write | chanx-go does |
| --- | --- |
| A struct per message | infers its JSON Schema, validates every frame, answers bad ones with an error frame |
| A method per handler | routes each frame by action, echoes the `ref` on replies, recovers panics |
| `Groups` and `ctx.Broadcast` | joins and leaves groups, fans out across processes over the layer |
| A topic struct | subscribe, unsubscribe, authorization, per-topic handlers, over one socket |
| `Authenticate` | runs it once, reports the result, closes with 4401 or 4403 on failure |
| Nothing more | an AsyncAPI 3 document, a docs page, and typed clients generated from it |

## Compared with what Go has

| Project | What it is | How it differs |
| --- | --- | --- |
| [gorilla/websocket](https://github.com/gorilla/websocket), [coder/websocket](https://github.com/coder/websocket) | WebSocket connections | The layer below. chanx-go runs on either |
| [melody](https://github.com/olahol/melody) | sessions and broadcast | No typed messages, no cross-process groups, no documentation |
| [Centrifuge](https://github.com/centrifugal/centrifuge) | a mature real-time pub/sub server | Its own protocol and SDKs; a broker, not typed request and reply handlers. The right pick for a pure pub/sub server |
| Socket.IO ports | events and rooms | Untyped payloads, no schema, the Socket.IO protocol |
| [asyncapi3](https://github.com/mitresthen/asyncapi3), [swaggest/go-asyncapi](https://github.com/swaggest/go-asyncapi) | AsyncAPI documents from Go types | Documents only, declared beside the server. chanx-go's comes from the handlers that run |

## One protocol, three languages

chanx-go is a third implementation of the chanx protocol, after Python and TypeScript.
That brings more than familiarity:

- **Clients work unchanged.** `@chanx-js/client` and the clients generated by
  `@chanx-js/codegen` or Python's `chanx generate-client` talk to a Go server as they do
  to a Python one.
- **One Redis, every language.** The Redis layer is wire-compatible with
  channels_redis, fast-channels and `@chanx-js/layers`. A Go worker can push to sockets
  held by a Django server, and the other way round.
- **Parity is tested, not claimed.** Validation errors, group names, key casing, the
  Redis encodings and the whole AsyncAPI document are checked against values recorded
  from Python chanx. The few deliberate differences are listed in
  [Differences from Python](/reference/differences).

## Who it is for

- Go teams building chat, notifications, live dashboards, collaboration or AI
  streaming, who want structure rather than a raw socket.
- Teams already on chanx in Python who move a service to Go, or run both side by side.
- Frontend teams who want a typed client generated from the server, not written by hand.
